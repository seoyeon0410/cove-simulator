# 코브 모션 웹 ↔ 실제 로봇 연동 가이드

전시 부스에서 여러 대의 코브(라즈베리파이 제로 제어기)를 한 대의 공유기에 연결해 운영할 때,
**모션 웹(코브 애니메이터)과 모터 움직임을 연동하기 위해 설계 엔지니어에게 받아야 할 것 / 전달할 것**을 정리한 문서입니다.
(웹 도구의 현재 데이터는 이 저장소의 코드 기준입니다: https://github.com/seoyeon0410/cove-simulator)

---

## 1. 목표와 전제

- 웹에서 만든 시나리오(모션 + 눈 표정)를 **실제 로봇이 같은 움직임으로 재생**한다.
- 여러 대가 **같은 시나리오를 동시에**(또는 로봇마다 다른 시나리오로) 움직인다.
- 센서(접근/터치)로 시나리오를 시작하는 전시 동작도 최종 목표로 둔다.
- 현재 웹은 **키네마틱(각도만) 시뮬레이터**입니다. 토크, 관성, 모터 속도 한계는 반영되어 있지 않으므로 로봇 쪽에서 속도·가속도 제한과 안전 처리가 필요합니다.

## 2. 3D 모델(GLB)에서 확인되는 로봇 구성 (추정 — 엔지니어 확인 필요)

| 구분 | GLB 부품명 | 추정 |
|---|---|---|
| 제어기 | RaspberryPiZeroW | 라즈베리파이 제로 W (2.4GHz Wi-Fi만 지원) |
| 모터 | XL,XC-330 / XM,H-430 idler (여러 개) | 다이나믹셀 XL330·XC330(소형), XM430·XH430(중형). 개수·ID는 확인 필요 |
| 모터 통신 | U2D2, U2D2PHB | USB→다이나믹셀(TTL/RS485) 변환기 + 전원 허브 보드 |
| 전원 | PD Power Module | USB-PD 전원 |
| 센서 | LD2410C mmWave | 사람 존재 감지 레이더 |
| 센서 | vl53l0x ×2 | ToF 거리 센서(머리 안 1개, 바디 쪽 1개) |
| 센서 | TTP223 ×3 | 정전식 터치 센서(머리 상단/좌우 추정) |
| 표시 | KeyStudio HT16K33 8×8 LED Matrix ×2 | 눈 (매트릭스 1개 = 눈 1개) |
| 구조 | 회전모터 브라켓, 베어링, 하부 회전판 | 바디 회전축 |

## 3. 웹이 다루는 관절 4개 (현재 모션 데이터의 전부)

각도는 **GLB 모델의 기본(접힌) 자세를 0°** 로 한 값입니다.

| 웹 이름 | 의미 | 회전축(모델) | 웹에서 쓴 범위 | 비고 |
|---|---|---|---|---|
| neck(기둥) | 목이 올라오는 정도 | 기둥 본의 로컬 Z | 0° ~ 35° | 0°=접힘(헤드가 폼 위에 얹힘), 클수록 위로 섬 |
| head(머리) | 헤드 앞뒤 기울기(피치) | 머리 본의 로컬 Z | −50° ~ +8° | 음수 = 얼굴이 위를 향함. 헤드가 수평일 때 대략 `head ≈ −1.2 × neck` |
| tilt(갸웃) | 헤드 좌우 기울임(롤) | 머리_갸웃 본의 로컬 Y(정면 축) | 약 −25° ~ +25° | 고개를 갸웃하는 동작 |
| body(몸통) | 바디 전체 좌우 회전(요) | 리그 루트의 수직축 | 약 −12° ~ +12° | 하부 회전판이 회전 |

- `IK_타겟` 본은 편집용 보조 값이라 로봇에 보낼 필요가 없습니다.
- 속도/가속도 참고치(시뮬레이션 모션 기준): 관절 최대 속도 약 60~90°/s, 최대 가속도 약 200~800°/s².
- **모터 ↔ 관절 매핑, 0점 오프셋, 회전 방향 부호, 감속비, 실제 가동 범위는 모델에 없습니다. 엔지니어에게 받아야 합니다.**
- 헤드가 하부 폼과 부딪히지 않도록 웹 쪽에서 헤드 각도를 보정해 두었지만(헤드–폼 충돌 보정), 실제 기구 간섭은 로봇 쪽 한계값으로도 막아야 합니다.

## 4. 웹이 가진 시나리오·표정 데이터

- 시간 해상도: 30fps, 모션 키는 0.1초 간격으로 구워져 있음(스프링 추종·미세 흔들림 포함).
- 클립은 **장면(구간)** 으로 나뉘며, 장면마다 상황/기분 설명과 표정 2가지가 있음.

| 클립 | 길이 | 장면 수(꼬리 구간 포함) |
|---|---|---|
| 시나리오1 휴식 | 23.8초 | 7 |
| 시나리오2 간지럽히기 | 51초 | 7 |
| 시나리오3 간식주기 | 37초 | 8 |
| 시나리오4 인사 | 19.8초 | 6 |
| 시나리오5 칭찬받기 | 20.8초 | 6 |
| 시나리오6 깜짝 놀람 | 20초 | 5 |
| 시나리오7 두리번 탐색 | 19.8초 | 6 |
| 시나리오8 작별 인사 | 21.8초 | 6 |
| 표정 모음 | 38.4초 | 16 (표정 1개 = 장면 1개) |

- 각 시나리오는 끝에 "다시 쉬어요" 같은 **제자리로 돌아오는 구간**이 붙어 있어 반복 재생해도 튀지 않습니다(시나리오6은 처음/끝 자세가 같음).

### 눈(8×8 LED) 표정 16종

뜬 눈, 감은 눈, 웃는 눈, 졸린 눈, 놀란 눈, 하트 눈, 반짝 눈, 슬픈 눈, 신난 눈, 윙크, 편안한 눈, 별 눈, 초롱 눈, 눈물 눈, 점 눈, 또렷한 눈

- 각 표정은 **8×8 도트 비트맵**입니다(코드: `look.js`의 `PATTERNS`). 예) 뜬 눈:
  ```
  00000000
  00011000
  00111100
  00111100
  00111100
  00011000
  00000000
  00000000
  ```
- 두 눈이 다른 모양인 표정(슬픈 눈, 신난 눈, 윙크)과, 여러 프레임이 도는 애니메이션(반짝 눈, 별 눈, 눈물 눈)이 있음.
- 깜빡임은 "뜬 눈"일 때 3.8초 주기로 5프레임(60ms 간격) 자동 재생(시간만으로 결정되므로 로봇에서도 같은 공식으로 재현 가능).
- 로봇에는 **표정 이름만 보내고 로봇이 비트맵을 갖고 있는 방식** 또는 **비트맵(8바이트×2)을 직접 보내는 방식** 중 선택(HT16K33 비트 배열 방향은 엔지니어 확인).

## 5. 연동 구조 제안

### 추천: B+C 혼합 — "로봇이 모션 파일을 갖고 재생, 웹은 지휘만"

```
[부스 PC/노트북: 웹 + 지휘 서버] ──Wi-Fi 공유기──┬─ 코브 #1 (Pi Zero W) ── U2D2 ── 다이나믹셀
                                                 ├─ 코브 #2 ...
                                                 └─ 코브 #N
```

1. **모션 파일 배포**: 웹이 시나리오를 JSON으로 내보내면 각 Pi에 한 번 복사(또는 시작 시 다운로드).
2. **재생 명령만 네트워크로**: 웹/지휘 서버가 `{robot, scenario, start_at}` 같은 짧은 명령을 보냄. Pi가 자체 시계로 파일을 재생 → Wi-Fi가 끊겨도 모션이 끊기지 않음.
3. **동기화**: 모든 Pi를 같은 NTP(부스 PC를 시간 서버로)에 맞추고 "현재 시각 + 0.5초"에 동시에 시작.
4. **센서 이벤트**: Pi → 지휘 서버로 `{robot, type: touch|presence|distance, value}` 전송 → 서버가 시나리오 선택.

대안
- **A. 실시간 스트리밍**(웹이 30Hz로 각도를 계속 전송): 구현은 가장 단순하고 "움직임 실시간 미리보기/조그(jog)"에 좋지만, 로봇 여러 대 + Wi-Fi에서는 끊김/지터에 취약. **초기 테스트·조정용**으로만 권장.
- **C. 완전 로컬**(웹 없이 Pi가 센서 보고 스스로 시나리오 선택): 가장 튼튼하지만 웹과의 연동이 약해짐.

전송 프로토콜 후보: WebSocket(웹과 직접 통신, 구현 쉬움) / MQTT(여러 대 지휘에 적합) / UDP 브로드캐스트(동시 시작 신호). 엔지니어가 Pi에서 이미 쓰는 방식이 있으면 그것에 맞춥니다.

## 6. 엔지니어에게 받아야 할 정보 (체크리스트)

**A. 하드웨어/모터**
1. 모터 개수, 모델명, **ID**, 각 모터가 어느 관절(neck/head/tilt/body)을 담당하는지
2. 통신: 프로토콜 2.0 여부, **보레이트**, U2D2 포트(`/dev/ttyUSB0` 등), 로봇마다 같은지
3. 제어 모드(위치/전류기반 위치/확장 위치), Profile Velocity·Acceleration 기본값
4. 관절별 **0점 위치(틱 값)**, 회전 방향 부호, 감속비, **실제 가동 한계(최소/최대)**
5. 토크/전류 제한, 과열·과부하 시 동작, 전원 인가 순서(홈 자세로 천천히 이동하는지)
6. 몸통 회전축이 무한 회전인지 제한 범위가 있는지(케이블 꼬임)

**B. 제어기/소프트웨어(Pi)**
7. OS/Python 버전, 이미 돌고 있는 제어 프로그램과 언어, 실행 방식(systemd 등)
8. Pi가 지금 받을 수 있는 명령 형식(예: HTTP/WebSocket/MQTT/UDP)과 포트
9. 모션 파일을 Pi에 올릴 수 있는 방법(SSH/SCP, 공유 폴더, HTTP 다운로드)
10. 좌표/각도 단위(도 vs 라디안 vs 다이나믹셀 틱)와 갱신 주기(Hz) 한계
11. 눈(HT16K33): I²C 주소 2개, 비트 배열(행/열 방향, 반전 여부), 밝기 설정
12. 센서(mmWave, vl53l0x, TTP223)를 읽는 코드와 이벤트 형식, 센서 임계값
13. 비상정지 방법(토크 OFF 명령), 통신이 끊겼을 때(워치독) 동작

**C. 네트워크**
14. 로봇 수(현재/최대), 공유기 기종, 2.4GHz 채널, SSID/보안
15. 로봇 IP 방식(고정 IP 또는 DHCP 예약), 이름 규칙(`cove-01` 등), mDNS 사용 여부
16. **클라이언트 격리(AP isolation)가 꺼져 있는지**, 같은 서브넷인지
17. 지휘용 PC/노트북이 같은 공유기에 연결되는지, 인터넷 연결 필요 여부(오프라인 전시)
18. 시간 동기: Pi 시계는 인터넷/NTP를 쓰는지(오프라인이면 부스 PC가 NTP 서버 역할 필요)

**D. 전시 운영**
19. 로봇별로 같은 시나리오를 동시에 vs 다르게 재생할지, 센서 트리거 규칙(스토리보드의 "0~50cm 안에서 1초 이상 감지" 등)
20. 전시 시간(하루 몇 시간 연속 가동), 전원 껐다 켰을 때 자동 시작 여부

## 7. 엔지니어에게 전달할 것

1. **관절 정의표**(위 3번)와 **각도 규약**: 0° = 접힌 기본 자세, 부호와 범위.
2. **모션 파일 형식 초안** (웹에서 내보내기 가능하도록 만들 수 있음):
   ```json
   {
     "version": 1,
     "clip": "시나리오3 간식주기",
     "fps": 30,
     "duration": 37,
     "joints": ["neck", "head", "tilt", "body"],
     "unit": "deg",
     "frames": [[0.0, 0, 0, 0, 0], [0.1, 0.3, -0.5, 0, 0]],
     "scenes": [{ "t": 0, "label": "누가 왔는지 살펴봐요" }],
     "eyes": [{ "t": 0, "expr": "졸린 눈" }, { "t": 1.2, "expr": "뜬 눈" }]
   }
   ```
   (`frames`는 `[시간(초), neck, head, tilt, body]`, 0.1초 간격. `eyes`는 표정 이름과 시작 시간.)
3. **표정 비트맵 표**(16종, 두 눈이 다른 것 포함)와 깜빡임/애니메이션 프레임 규칙.
4. 시나리오 목록과 길이(위 4번), 센서 트리거로 시작하고 싶은 시나리오 조건표.
5. 원하는 **통신 방식 제안**(위 5번)과 안전 요구사항(속도·가속도 상한, 한계값 클램프, 워치독, 비상정지).

## 8. 제가(Claude) 직접 제어하려면 필요한 것

제가 할 수 있는 일은 **코드 작성, 이 PC에서 명령 실행, 이 PC에서 네트워크 접속**입니다. 로봇을 직접 움직이려면 아래가 필요합니다.

1. **이 컴퓨터가 로봇과 같은 공유기에 연결**되어 있어야 합니다(제가 쓰는 환경은 이 컴퓨터입니다).
2. 각 로봇의 **주소**(IP 또는 `cove-01.local`)와 **접속 방법**: SSH 키 방식 접속(비밀번호는 저에게 알려주지 말고, 키 또는 미리 설정된 접속으로), 또는 로봇이 받는 API 주소·포트와 명령 형식.
3. 위 6번의 **모터 ID·0점·부호·한계값**과 통신 설정(보레이트, 포트).
4. **로봇 쪽 수신 프로그램**: 엔지니어가 이미 갖고 있으면 그 명세를 받고, 없으면 제가 Pi용 Python 서비스(다이나믹셀 SDK + 명령 수신 + 재생 + 한계 클램프 + 워치독 + 눈 LED 제어)를 작성합니다. Pi에 설치/실행은 엔지니어 또는 사용자 승인 하에 진행합니다.
5. **안전 조건**: 처음에는 **로봇 1대, 토크 제한을 낮추고, 사람이 옆에서 전원/비상정지에 손이 닿는 상태**로 시험합니다. 로봇이 움직이는 모든 명령은 사용자가 확인한 뒤에 실행합니다.
6. 제가 코드로 확인할 수 없는 것: 실제 모터의 움직임·소리·간섭은 **사람이 눈으로 확인하고 알려주셔야** 합니다.

|---|---|---|

| 1 | 로봇 1대 연결 테스트: 눈 켜기 → 관절 하나씩 조그(소각도) | IP, 모터 ID/한계 |

| 3 | 시나리오 1~8 재생, 속도·가속도 한계 튜닝, 눈 동기 | 현장 로봇 |

## 10. 전시 현장 체크리스트

- 공유기: 2.4GHz 전용 채널 고정, 클라이언트 격리 끔, 로봇 IP 예약, 전시장 다른 Wi-Fi와 채널 겹침 확인
- 로봇 전원 투입 시 항상 **홈(접힌) 자세에서 시작**, 투입 직후 갑작스러운 움직임 방지
- 비상정지(전체 토크 OFF) 버튼을 지휘 화면과 현장에 각각 준비
- 연결이 끊기면 로봇이 **현재 시나리오를 끝내고 제자리**로 돌아오게(또는 즉시 제자리로)
- 하루 가동 후 모터 온도/전류 로그 확인, 케이블(특히 몸통 회전부) 점검
- 관람객이 만지는 센서(터치) 반응 후 **재시작 대기 시간**(연타 방지)
